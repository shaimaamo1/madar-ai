## Contracts and identity

`POST /api/bridge/enterprise/context` accepts kind, stable event ID and customer reference. Intake additionally accepts a validated lead/message; appointment requires an explicit Booking. `POST /api/bridge/enterprise/commit` revalidates authority and stores idempotent evidence; untrusted analysis never grants consent or books outside backend checks. `POST /api/bridge/enterprise/failure` records redacted identifiers and revokes a failed demo capability. CRM intake shares existing webhook receipts and delivery keys with `/api/integrations/ingest` and signed provider adapters. Repeat events cannot create duplicate messages/queue entries.

Bridge requests authenticate with the server-managed MADAR bridge header credential. Ordinary integration calls remain bound to the configured integration tenant. A dashboard demo cannot supply arbitrary tenant/contact IDs: it queues an isolated fictional run, and `POST /api/bridge/demo/claim` issues a short-lived capability tied to that run/event/tenant. Scenario details are server-controlled, steps are ordered, failures/expiry revoke capability. Full Demo invokes the eight real modules, stores the actual parent execution reference and remains Awaiting verification until the backend checks successful n8n execution data against the exact demo run ID.

The importer keeps workflows inactive, preflights duplicates/active conflicts, resolves `MADAR_WORKFLOW:` submodule references and binds Error Monitor. [Versioned initial-ten identities](../scripts/workflow_identity_versions.json) preserve recovery after expansion when a manifest is lost; the older four-workflow registry remains supported. API keys remain private local configuration; no Graph/model key is embedded in exports. Windows setup creates only MADAR's app container and reuses the existing n8n.

## Supporting modules

Full Demo (11 nodes) orchestrates real fictional outcomes. Delivery Reconciliation (5), WhatsApp Delivery (5), Error Monitor (3), Ingestion Subworkflow (3) and Test Evaluation (3) retain their focused contracts. WhatsApp delivery remains independently gated by authorization, consent, opt-out, ownership, Meta service windows/templates, sandbox blocking and retry/uncertain-outcome policies. Raw Meta requests terminate at MADAR's HMAC-verified webhook, never an unsigned n8n JSON trigger.

Automatic n8n Error Workflow invocation does not run for manual/CLI executions. The business modules therefore record their own failures explicitly; the importer-bound Error Monitor remains available for authorized automatic execution. Customer workflows retain no success/error payloads. Only the server-controlled **fictional Full Demo** keeps successful evidence because n8n otherwise removes the execution record; its capability is invalidated before success, and failed payload retention remains disabled.

## Local operation and presentation

Run the existing Windows Update-Madar.cmd / Start-Madar.cmd. All fourteen exports are prepared/imported automatically into the existing n8n without activation. In a fictional dashboard workspace, queue Full Demo in System Health, execute the imported inactive **MADAR Full Demo** in n8n, and verify it from the dashboard. One local editor action is necessary because the supported public API cannot arbitrarily run inactive workflows; no private editor endpoints or automatic activation are introduced.
