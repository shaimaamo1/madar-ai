# Integrations and access

Only website chat and internal CRM operations are verified locally. The official provider adapters are implemented and exercised with signed fixture requests. Live n8n, Telegram, Meta, and language-model accounts have not been connected or verified. No messages have been sent to real customers.

## Self-hosted n8n

The supplied Cloud trial API is unavailable. MADAR now targets your existing local self-hosted n8n. No Cloud-to-localhost connection is attempted. Follow [local Docker setup](local-development.md): the local wizard securely reads `N8N_API_KEY`, configures Docker networking, checks API access, and deploys inactive workflows. Cloud dashboard preview leaves `N8N_ENABLED=false`.

| Importable workflow | Behavior |
| --- | --- |
| MADAR Follow-up Scheduler | Evaluates due follow-ups every five minutes, then calls the approval-gated dispatcher |
| MADAR Test Evaluation | Manual evaluation with no dispatch node |
| MADAR Ingestion Subworkflow | Shared authenticated lead normalization for external source workflows |
| MADAR Error Monitor | Produces a redacted incident summary in n8n execution logs |

The JSON files in `workflows/` are generated by `scripts/generate_workflows.py`, contain no secret values, and default inactive. They use versioned n8n nodes, `executionOrder=v1` and bounded retries. Structural validation and mocked API deployment pass; execution on your n8n version remains a local test. The deployment helper creates encrypted Header Auth credentials, attaches the error workflow and maintains an instance-specific manifest to update inactive workflows without duplicates. It never activates them and refuses to overwrite an active managed workflow.

`MADAR_N8N_APP_URL` is the callback address reachable from n8n; `N8N_BASE_URL` is the address reachable from the caller. These differ between host and Docker. Local setup binds ingestion/bridge operations to workspace `madar` using `MADAR_INTEGRATION_WORKSPACE`; an explicit `MADAR_INTEGRATION_TENANT_ID` takes precedence. Tokens authenticate the bridge and ingestion endpoints, while `N8N_API_KEY` grants n8n management access. All remain in ignored local settings and n8n's credential store. The optional `MADAR_AI_API_KEY` is an OpenAI provider key and is not needed for these features; see the key table in the local guide.

## WhatsApp, Facebook, Instagram

`GET /webhooks/meta` implements Meta’s verification challenge; `POST /webhooks/meta` verifies `X-Hub-Signature-256` over the exact raw body. WhatsApp text events, message delivery statuses, Messenger/Instagram text events, and Facebook Lead Ads events are normalized. Lead Ads data is fetched using the authorized Page token. Replayed message events are deduplicated transactionally.

WhatsApp variables: `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_VERIFY_TOKEN`, `META_APP_SECRET`, and `MADAR_INTEGRATION_TENANT_ID`. Page messaging/Lead Ads also need `META_PAGE_ACCESS_TOKEN` and relevant Page subscriptions and app permissions. The signature secret and verify token must be actual local secure values, because local HMAC verification cannot work with proxy placeholders. The access token can use a supported scoped HTTPS proxy binding for `graph.facebook.com`.

The app uses official Graph API endpoints. Free-form delivery requires a recent inbound channel message; approved WhatsApp template messages require recorded consent. Template creation/approval happens in Meta; this release queues approved parameter-free templates through `/api/integrations/whatsapp/template`. Provider policies may be stricter than these local guards. Re-check the Graph API version and messaging rules for the approved Meta application before connecting. Attachments, interactive buttons, media, payment flows, template parameters, business verification, and app review are not implemented.

Direct Meta authorization cannot be initiated here: no Meta connector, application ID, authorized business, or approved public HTTPS callback exists. A supported BSP is a viable future account route but also needs authorization, a provider contract, and possibly paid service approval. No unofficial WhatsApp automation is used.

## Telegram

Set `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, and the integration tenant securely. `POST /webhooks/telegram` checks the Telegram secret header and processes private text messages. Duplicate `update_id` values have no repeated CRM effects. The official `sendMessage` adapter uses the same outbox and approval gate. Telegram requires its bot token inside the HTTPS path; use a real securely injected token in the deployed process unless the platform explicitly supports path-token substitution. Do not log request URLs.

After an approved HTTPS callback exists, the official `setWebhook` call must target `/webhooks/telegram` with that secret. Registration is not executed without bot authorization. `getMe` is available through the dashboard’s read-only Verify access action. Bot registration requires account action via BotFather if no bot already exists; credentials should be supplied securely, never in chat.

## Website chat, forms, email, CRM

The public portal is served at `/chat?company=WORKSPACE_SLUG`. It creates an anonymous lead, qualifies the inquiry, returns verified matches, lists available viewing times, and books a viewing without granting dashboard access. Public session capabilities cannot access another tenant’s records. HTTPS sites may embed the public portal in an iframe; the authenticated dashboard rejects cross-origin framing. Apply deployment-level anti-abuse limits for production.

Public website forms can submit `POST /api/public/lead` with `{ "tenant_slug": "company-slug", "lead": { "name": "Customer", "email": "customer@example.com", "consent": false } }`. The response discloses no contact identity or history access. Authenticated CRM systems and email workflows can submit `POST /api/integrations/ingest` with `Authorization: Bearer MADAR_INGEST_TOKEN` and this shape:

```json
{"event_id":"provider-unique-id","lead":{"name":"Customer","email":"customer@example.com","source":"email","consent":false},"text":"Customer inquiry"}
```

An existing public chat session can retrieve its conversation using `/api/public/history`. The ingestion API receives normalized email/CRM events; connecting an inbox or CRM account still requires its own authorized source workflow. Native IMAP, SMTP delivery, and vendor-specific CRM synchronization are not connected. Tokens never grant arbitrary tenant selection. A separate integration deployment/binding is required for each tenant’s provider channels in this release.

External delivery defaults to `MADAR_ALLOW_EXTERNAL_SEND=false`. Turning it on requires explicit owner approval, provider test-account verification, and a review of consent and recipient restrictions. HTTP 429/5xx retries use backoff with a five-attempt cap. Ambiguous connection failures are held for reconciliation, avoiding blind duplicate sends.

Language-model access verification uses a read-only models request. Actual inference also requires the separate `MADAR_ALLOW_MODEL_USAGE=true` opt-in after the owner approves any API usage cost. Supplying an API key alone does not enable billable inference.
